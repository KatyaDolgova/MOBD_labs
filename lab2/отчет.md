# Лабораторная работа №2. Базовые SQL-запросы и фильтрация данных

## 1. Наполнение таблиц данными


Для массового заполнения используется `generate_series` в сочетании с `random()`: функция `generate_series(1, N)` возвращает N строк-счётчиков, каждая из которых превращается в одну строку будущей таблицы, а `random()` подставляет в неё случайные, но согласованные значения.

Чтобы случайный родитель (продавец, категория, товар, пользователь) выбирался **по-разному для каждой строки**, id родительской таблицы собираются в массив (`array_agg`), и из него берётся элемент по случайному индексу: `ids[floor(random() * n)::int + 1]`. Это надёжнее, чем подзапрос вида `ORDER BY random() LIMIT 1`, который PostgreSQL может вычислить один раз на весь запрос и присвоить одно и то же значение всем строкам.

Связи между таблицами соблюдены: цена товара в позиции заказа копируется из `products` в момент «покупки», сумма заказа `total_amount` пересчитывается из его позиций, платёж и доставка создаются только для заказов с подходящим статусом, адрес и отзыв - только для пользователей, у которых есть соответствующие заказы. Скрипт выполняется одной транзакцией (`BEGIN ... COMMIT`), чтобы при ошибке на любом шаге база не осталась частично заполненной.


### Примеры заполнения таблиц


**users** - пользователи; первые 30 (id 1-30) получили роль `seller_owner`, остальные - `customer`. `generate_series(1, 200)` даёт 200 строк-счётчиков `g`, `CASE WHEN` раздаёт роли, `lpad` дополняет номер телефона нулями до 7 цифр:

```sql
INSERT INTO users (full_name, email, phone, role)
SELECT
    'Пользователь ' || g,
    'user' || g || '@example.com',
    '+7900' || lpad(g::text, 7, '0'),
    CASE WHEN g <= 30 THEN 'seller_owner' ELSE 'customer' END
FROM generate_series(1, 200) AS g;
```

| id | full_name | email | phone | role |
|---|---|---|---|---|
| 1 | Пользователь 1 | user1@example.com | +79000000001 | seller_owner |
| 31 | Пользователь 31 | user31@example.com | +79000000031 | customer |

**sellers** - магазин на каждого `seller_owner`; `user_id` - внешний ключ на `users.id`. Данные читаются из уже вставленных пользователей:

```sql
INSERT INTO sellers (user_id, store_name, description)
SELECT id, 'Магазин №' || id, 'Описание магазина ' || id
FROM users
WHERE role = 'seller_owner';
```

| id | user_id | store_name |
|---|---|---|
| 1 | 1 | Магазин №1 |
| 2 | 2 | Магазин №2 |

**categories** - корневая категория и её подкатегория (самоссылка через `parent_id`). Сначала вставляются 5 корней, затем `CROSS JOIN generate_series(1, 3)` превращает каждый корень в 3 подкатегории:

```sql
INSERT INTO categories (parent_id, name) VALUES
    (NULL, 'Электроника'), (NULL, 'Одежда'), (NULL, 'Книги'),
    (NULL, 'Дом и сад'), (NULL, 'Спорт');

INSERT INTO categories (parent_id, name)
SELECT c.id, c.name || ' / Подкатегория ' || g
FROM categories c
CROSS JOIN generate_series(1, 3) AS g
WHERE c.parent_id IS NULL;
```

| id | parent_id | name |
|---|---|---|
| 1 | - | Электроника |
| 6 | 1 | Электроника / Подкатегория 1 |

**products** - `seller_id` и `category_id` выбраны случайным индексом из массивов существующих id. `WITH`  `s` и `c` собирают все id продавцов и подкатегорий в массивы одной строкой, а `FROM generate_series(1, 1200) AS g, s, c` (запятая = `CROSS JOIN`) делает эти массивы доступными для каждой из 1200 строк:

```sql
WITH s AS (SELECT array_agg(id) AS ids, count(*) AS n FROM sellers),
     c AS (SELECT array_agg(id) AS ids, count(*) AS n
           FROM categories WHERE parent_id IS NOT NULL)
INSERT INTO products (seller_id, category_id, title, description, price, is_active)
SELECT
    s.ids[floor(random() * s.n)::int + 1],
    c.ids[floor(random() * c.n)::int + 1],
    'Товар №' || g,
    'Описание товара ' || g,
    (random() * 49000 + 100)::numeric(12,2),
    (random() > 0.1)
FROM generate_series(1, 1200) AS g, s, c;
```

| id | seller_id | category_id | title | price | is_active |
|---|---|---|---|---|---|
| 1 | 5 | 6 | Товар №1 | 23115.70 | t |
| 2 | 19 | 20 | Товар №2 | 34214.08 | f |

**stock** - по одной записи остатка на каждый товар (`product_id` - и первичный, и внешний ключ):

```sql
INSERT INTO stock (product_id, quantity)
SELECT id, (random() * 200)::int FROM products;
```

| product_id | quantity |
|---|---|
| 1 | 4 |
| 2 | 66 |

**carts / cart_items** - корзина у 150 случайных пользователей из 200, в каждой до 3 случайных товаров. `ORDER BY random() LIMIT 150` перемешивает всех пользователей и берёт первые 150 без повторов; `ON CONFLICT DO NOTHING` в `cart_items` пропускает товар, если он случайно выпал повторно в той же корзине:

```sql
INSERT INTO carts (user_id)
SELECT id FROM users ORDER BY random() LIMIT 150;

WITH p AS (SELECT array_agg(id) AS ids, count(*) AS n FROM products)
INSERT INTO cart_items (cart_id, product_id, quantity)
SELECT c.id, p.ids[floor(random() * p.n)::int + 1], (random() * 3 + 1)::int
FROM carts c
CROSS JOIN generate_series(1, 3) AS slot
CROSS JOIN p
ON CONFLICT (cart_id, product_id) DO NOTHING;
```

| carts.id | carts.user_id |
|---|---|
| 1 | 70 |

| cart_items.cart_id | cart_items.product_id | cart_items.quantity |
|---|---|---|
| 1 | 172 | 3 |
| 1 | 1026 | 2 |

`orders` - 1000 заказов; пользователь и статус выбраны случайно, дата - в пределах последних 150 дней:

```sql
WITH u AS (SELECT array_agg(id) AS ids, count(*) AS n FROM users)
INSERT INTO orders (user_id, status, created_at)
SELECT
    u.ids[floor(random() * u.n)::int + 1],
    (ARRAY['created','paid','sent','delivered','cancelled'])[floor(random() * 5 + 1)],
    now() - (random() * interval '150 days')
FROM generate_series(1, 1000) AS g, u;
```

| id | user_id | status | total_amount | created_at |
|---|---|---|---|---|
| 8 | 173 | delivered | 141264.93 | 2026-09-23 09:38:18+03 |

`order_items` - до 3 позиций на заказ;  индекс товара `pick.idx` вычисляется один раз через `LATERAL` и используется и для `product_id`, и для `unit_price`, поэтому цена всегда соответствует выбранному товару:

```sql
WITH p AS (SELECT array_agg(id) AS ids, array_agg(price) AS prices, count(*) AS n FROM products)
INSERT INTO order_items (order_id, product_id, quantity, unit_price)
SELECT o.id, p.ids[pick.idx], (random() * 3 + 1)::int, p.prices[pick.idx]
FROM orders o
CROSS JOIN generate_series(1, 3) AS slot
CROSS JOIN p
CROSS JOIN LATERAL (
    SELECT floor(random() * p.n)::int + 1 + (o.id - o.id) + (slot - slot) AS idx
) AS pick
ON CONFLICT (order_id, product_id) DO NOTHING;
```

| order_id | product_id | quantity | unit_price |
|---|---|---|---|
| 8 | 720 | 3 | 24480.18 |
| 8 | 856 | 3 | 1855.66 |
| 8 | 884 | 3 | 20752.47 |

`total_amount` пересчитан отдельным шагом `UPDATE` именно из этих трёх строк:

```sql
UPDATE orders o
SET total_amount = COALESCE(
    (SELECT SUM(oi.quantity * oi.unit_price)
       FROM order_items oi WHERE oi.order_id = o.id),
    0
);
```

`payments` - оплата создаётся только для заказов со статусом `paid`/`sent`/`delivered`; здесь он `delivered`, поэтому платёж есть. `amount` равен `total_amount`, `paid_at` на час позже `created_at`:

```sql
INSERT INTO payments (order_id, amount, status, paid_at)
SELECT o.id, o.total_amount, 'succeeded', o.created_at + interval '1 hour'
FROM orders o
WHERE o.status IN ('paid','sent','delivered') AND o.total_amount > 0;
```

| id | order_id | amount | status | paid_at |
|---|---|---|---|---|
| 5 | 8 | 141264.93 | succeeded | 2026-09-23 10:38:18+03 |

`addresses` - один адрес на каждого пользователя, у которого есть хотя бы один заказ (`DISTINCT ON (o.user_id)`):

```sql
INSERT INTO addresses (user_id, city, street, house, apartment)
SELECT DISTINCT ON (o.user_id)
    o.user_id,
    (ARRAY['Москва','Санкт-Петербург','Казань','Новосибирск','Екатеринбург'])[floor(random() * 5 + 1)],
    'ул. Тестовая',
    (floor(random() * 100) + 1)::text,
    (floor(random() * 200) + 1)::text
FROM orders o
ORDER BY o.user_id;
```

| id | user_id | city | street | house | apartment |
|---|---|---|---|---|---|
| 171 | 173 | Санкт-Петербург | ул. Тестовая | 7 | 90 |

`deliveries` - доставка заказа на адрес; `JOIN addresses a ON a.user_id = o.user_id` гарантирует, что доставка идёт на адрес того же пользователя, который оформил заказ; статус `delivered`, т. к. и заказ `delivered`:

```sql
INSERT INTO deliveries (order_id, address_id, delivery_status, delivery_date)
SELECT
    o.id, a.id,
    CASE WHEN o.status = 'delivered' THEN 'delivered' ELSE 'in_transit' END,
    o.created_at + interval '3 days'
FROM orders o
JOIN addresses a ON a.user_id = o.user_id
WHERE o.status IN ('sent','delivered');
```

| id | order_id | address_id | delivery_status | delivery_date |
|---|---|---|---|---|
| 354 | 8 | 171 | delivered | 2026-09-26 09:38:18+03 |

`reviews` - отзыв пользователя  на товар из его доставленного заказа; `DISTINCT ON (user_id, product_id)` даёт не более одного отзыва на пару, `ORDER BY ..., random()` при нескольких подходящих заказах выбирает случайный:

```sql
INSERT INTO reviews (user_id, product_id, score, comment, created_at)
SELECT DISTINCT ON (o.user_id, oi.product_id)
    o.user_id, oi.product_id,
    floor(random() * 5 + 1)::int,
    'Отзыв пользователя ' || o.user_id,
    o.created_at + interval '5 days'
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status = 'delivered'
ORDER BY o.user_id, oi.product_id, random()
ON CONFLICT (user_id, product_id) DO NOTHING;
```

| id | user_id | product_id | score | comment |
|---|---|---|---|---|
| 561 | 173 | 267 | 5 | Отзыв пользователя 173 |

## 3. Фильтрация по нескольким условиям: AND и OR со скобками

**Цель.** Найти активные товары, которые либо очень дешёвые (до 5000), либо очень дорогие (от 40000).

```sql
SELECT id, title, price
FROM products
WHERE (price < 5000 OR price > 40000)
  AND is_active = TRUE
ORDER BY price;
```

Скобки обязательны: `AND` связывает сильнее `OR`. Без скобок `price < 5000 OR price > 40000 AND is_active = TRUE` прочиталось бы как `price < 5000 OR (price > 40000 AND is_active = TRUE)`, и дешёвые неактивные товары попали бы в результат.

## 4. Предикаты BETWEEN, IN, LIKE/ILIKE, IS NULL

### 4.1 BETWEEN - замкнутый диапазон

**Цель.** Товары в ценовом диапазоне от 10000 до 20000 рублей включительно.

```sql
SELECT id, title, price
FROM products
WHERE price BETWEEN 10000 AND 20000
ORDER BY price
LIMIT 10;
```

| id | title | price |
|---|---|---|
| 354 | Товар №354 | 10045.29 |
| 1079 | Товар №1079 | 10063.69 |
| 93 | Товар №93 | 10154.59 |
| 9 | Товар №9 | 10247.58 |
| 47 | Товар №47 | 10253.96 |
| 813 | Товар №813 | 10262.08 |
| 670 | Товар №670 | 10370.00 |
| 839 | Товар №839 | 10378.16 |

`BETWEEN a AND b` равносильно `price >= 10000 AND price <= 20000`, но короче и нагляднее.

### 4.2 IN - принадлежность списку значений

**Цель.** Товары из трёх конкретных подкатегорий.

```sql
SELECT id, title, category_id
FROM products
WHERE category_id IN (6, 9, 11)
ORDER BY id
LIMIT 10;
```

| id | title | category_id |
|---|---|---|
| 1 | Товар №1 | 6 |
| 3 | Товар №3 | 9 |
| 5 | Товар №5 | 9 |
| 6 | Товар №6 | 9 |
| 10 | Товар №10 | 11 |
| 19 | Товар №19 | 11 |
| 24 | Товар №24 | 9 |
| 28 | Товар №28 | 9 |

`category_id IN (6, 9, 11)` равносильно `category_id = 6 OR category_id = 9 OR category_id = 11`, но короче.

### 4.3 LIKE - шаблон с % и _ 

**Цель.** Найти товары, чьё название начинается на «Товар №12».

```sql
SELECT id, title
FROM products
WHERE title LIKE 'Товар №12%'
ORDER BY id;
```

| id | title |
|---|---|
| 12 | Товар №12 |
| 120 | Товар №120 |
| 121 | Товар №121 |
| 122 | Товар №122 |
| 123 | Товар №123 |
| 124 | Товар №124 |
| 125 | Товар №125 |
| 126 | Товар №126 |

`%` заменяет любую последовательность символов (в том числе пустую), поэтому шаблону соответствуют и «Товар №12», и «Товар №120»…«Товар №129», и «Товар №1200».

### 4.4 ILIKE - то же без учёта регистра

**Цель.** Найти пользователей с email на домене example.com, независимо от регистра букв.

```sql
SELECT id, email
FROM users
WHERE email ILIKE '%EXAMPLE.com'
ORDER BY id
LIMIT 5;
```

| id | email |
|---|---|
| 1 | user1@example.com |
| 2 | user2@example.com |
| 3 | user3@example.com |
| 4 | user4@example.com |
| 5 | user5@example.com |

`ILIKE` отличается от `LIKE` только тем, что не учитывает регистр: нашёл бы и `User1@Example.Com`.

### 4.5 IS NULL - заказы без оплаты

**Цель.** Найти заказы, по которым ещё нет платежа.

```sql
SELECT o.id AS order_id, o.status
FROM orders AS o
LEFT JOIN payments AS p ON p.order_id = o.id
WHERE p.id IS NULL
ORDER BY o.id
LIMIT 10;
```

| order_id | status |
|---|---|
| 2 | created |
| 4 | created |
| 7 | created |
| 10 | created |
| 11 | created |
| 12 | cancelled |
| 13 | created |
| 14 | cancelled |

`LEFT JOIN` сохраняет все заказы, даже те, для которых нет подходящей строки в `payments`; у таких заказов столбец `p.id` окажется `NULL`. Условие `p.id IS NULL` отбирает именно их. Сравнение `p.id = NULL` для этого не подошло бы: оно всегда даёт `UNKNOWN`, и строка в результат не попадёт.

## 5. Сортировка по двум столбцам в разных направлениях

**Цель.** Товары по категориям в алфавитном/числовом порядке по возрастанию, а внутри каждой категории - от дорогих к дешёвым.

```sql
SELECT
    p.category_id,
    c.name AS category_name,
    p.title,
    p.price
FROM products AS p
JOIN categories AS c ON c.id = p.category_id
ORDER BY p.category_id ASC, p.price DESC
```

## 6. Постраничный вывод: LIMIT и OFFSET

**Цель.** Показать каталог товаров по 15 позиций на странице.

Формула смещения: `OFFSET = (номер_страницы − 1) × размер_страницы`.

```sql
-- Страница 1 (записи 1-15)
SELECT id, title, price FROM products ORDER BY title ASC LIMIT 15 OFFSET 0;

-- Страница 2 (записи 16-30)
SELECT id, title, price FROM products ORDER BY title ASC LIMIT 15 OFFSET 15;

-- Страница 3 (записи 31-45)
SELECT id, title, price FROM products ORDER BY title ASC LIMIT 15 OFFSET 30;
```

Начало страницы 1:

| id | title | price |
|---|---|---|
| 1 | Товар №1 | 23115.70 |
| 10 | Товар №10 | 26138.51 |
| 100 | Товар №100 | 47238.94 |
| 1000 | Товар №1000 | 6835.98 |
| 1001 | Товар №1001 | 31289.39 |

Начало страницы 2:

| id | title | price |
|---|---|---|
| 1011 | Товар №1011 | 36556.23 |
| 1012 | Товар №1012 | 2391.69 |
| 1013 | Товар №1013 | 22961.09 |
| 1014 | Товар №1014 | 29307.68 |
| 1015 | Товар №1015 | 10506.42 |

`ORDER BY title ASC` обязателен: названия товаров сортируются как текст (`'1000'` идёт раньше `'11'`, потому что сравнение строковое, а не числовое), но порядок при этом фиксированный и одинаковый между запросами - без `ORDER BY` PostgreSQL не гарантирует, что страницы не будут повторяться или терять строки.

## 7. Контрольные вопросы

### 1. Из каких секций состоит команда SELECT и в каком порядке они логически выполняются?

Текст запроса пишется в порядке `SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT/OFFSET`, но **выполняется** в другом порядке:

1. `FROM` - определяются источники, выполняются `JOIN`.
2. `WHERE` - строки фильтруются построчно, до группировки.
3. `GROUP BY` - строки группируются.
4. `HAVING` - фильтруются уже сами группы.
5. `SELECT` - вычисляются столбцы и выражения, присваиваются псевдонимы.
6. `DISTINCT` - убираются полные дубликаты строк результата.
7. `ORDER BY` - сортировка.
8. `LIMIT/OFFSET` - отбор диапазона строк.

### 2. Почему в промышленных запросах не рекомендуется использовать SELECT *?

- Передаются лишние столбцы - лишний трафик и память, особенно на `TEXT`-полях вроде `description`.
- Код становится хрупким: при добавлении нового столбца в таблицу набор возвращаемых полей незаметно меняется, и код, рассчитанный на фиксированный порядок столбцов, может сломаться.
- Мешает оптимизации: PostgreSQL не может ограничиться только нужными столбцами (index-only scan), если запрошены все поля.
- При `JOIN` двух таблиц с одинаковыми именами столбцов возникает неоднозначность.
- Явный список столбцов (`SELECT title AS name, price`) понятнее читателю: сразу видно, что использует запрос.

### 3. Для чего предназначена секция WHERE и как в ней комбинируются условия?

`WHERE` отбирает строки, которые попадут в результат, **до группировки**: строка остаётся, если условие даёт `TRUE`. Условия комбинируются логическими операторами:

- `AND` - оба условия должны быть истинны;
- `OR` - достаточно одного;
- `NOT` - инверсия.

`AND` связывает сильнее `OR`, поэтому при их смешивании порядок вычисления нужно явно задавать скобками, как в пункте 3 отчёта: `WHERE (price < 5000 OR price > 40000) AND is_active = TRUE`.

### 4. Чем предикаты BETWEEN и IN отличаются от записи тех же условий через операторы сравнения и OR?

Это та же самая логика, но в более короткой и наглядной записи - транслируется в идентичное условие.

- `price BETWEEN 10000 AND 20000` ≡ `price >= 10000 AND price <= 20000` (диапазон замкнутый, границы включаются).
- `category_id IN (6, 9, 11)` ≡ `category_id = 6 OR category_id = 9 OR category_id = 11`.

Разница не в результате выполнения и не в производительности (планировщик PostgreSQL оптимизирует обе формы одинаково), а в удобстве и устойчивости к ошибкам: не нужно повторять имя столбца в каждом условии цепочки.

### 5. Как работает оператор LIKE и что означают символы % и _ в шаблоне?

`LIKE` сравнивает строку с шаблоном. Два специальных символа:

- `%` - любая последовательность символов, включая пустую;
- `_` - ровно один произвольный символ.

`title LIKE 'Товар №12%'` совпадёт с «Товар №12», «Товар №120», «Товар №1234» - всё, что начинается с «Товар №12», а дальше что угодно. `LIKE` чувствителен к регистру; `ILIKE` выполняет то же сопоставление без учёта регистра.

### 6. Что такое трёхзначная логика и почему нельзя проверять значение на NULL оператором «=»?

В SQL условие может принимать не два, а три значения: `TRUE`, `FALSE` и `UNKNOWN`. `UNKNOWN` возникает при сравнении с `NULL`, потому что `NULL` означает «значение неизвестно», а не «пусто» или «ноль»: неизвестно, равны ли два неизвестных значения.

`NULL = NULL` → `UNKNOWN`, `5 = NULL` → `UNKNOWN`. Строка с условием `UNKNOWN` в `WHERE` не попадает в результат - так же, как и при `FALSE`. Поэтому `WHERE price = NULL` никогда не найдёт строки, даже если `price` действительно `NULL`.

Для проверки отсутствия значения служат специальные предикаты `IS NULL` и `IS NOT NULL`, которые возвращают честные `TRUE`/`FALSE`. 

### 7. Что делает секция ORDER BY и как задать сортировку по убыванию и положение NULL?

`ORDER BY` упорядочивает строки результата по одному или нескольким столбцам или выражениям. Направление задаётся `ASC` (по возрастанию, умолчание) и `DESC` (по убыванию); для разных ключей сортировки направление можно задавать отдельно, как в пункте 5: `ORDER BY p.category_id ASC, p.price DESC`.

Положение `NULL` в сортировке по умолчанию - «больше всех остальных значений»: при `ASC` он окажется в конце, при `DESC` - в начале. Это можно задать явно: `ORDER BY price ASC NULLS FIRST` или `ORDER BY price DESC NULLS LAST`.

### 8. Для чего служат LIMIT и OFFSET и как с их помощью организовать постраничный вывод?

`LIMIT n` ограничивает результат первыми `n` строками после сортировки; `OFFSET m` пропускает первые `m` строк перед началом вывода. Вместе они реализуют постраничный вывод: для страницы размера `p` номер страницы `k` соответствует `LIMIT p OFFSET (k-1)*p`

Важное условие - обязательный `ORDER BY`: без фиксированного порядка PostgreSQL не гарантирует одинаковое расположение строк между двумя отдельными запросами, и страницы могут повторяться или теряться. Также стоит помнить, что большой `OFFSET` неэффективен: СУБД всё равно вычисляет и отбрасывает пропускаемые строки, просто не возвращает их.

### 9. Что делает ключевое слово DISTINCT?

`DISTINCT` убирает из результата полностью совпадающие строки, оставляя только уникальные комбинации выбранных столбцов.

Отличие от `DISTINCT ON (столбцы)`: обычный `DISTINCT` сравнивает все выбранные столбцы целиком, а `DISTINCT ON` оставляет одну строку на каждую уникальную комбинацию указанных столбцов, даже если другие столбцы различаются (при этом нужен `ORDER BY`, чтобы определить, какая из нескольких подходящих строк останется). Такой приём используется в скрипте наполнения - например, для выбора одного адреса на пользователя.

### 10. Как сгенерировать большой объём тестовых данных средствами PostgreSQL?

Базовый инструмент - `generate_series(start, stop)`: функция-источник строк, возвращающая одну строку на каждое число диапазона; используется в `FROM` как источник нужного количества строк (`generate_series(1, 1200)` даёт 1200 строк для вставки 1200 товаров).

Для разнообразия значений применяются:

- `random()` - случайное число от 0 до 1, вычисляется отдельно для каждой строки, если стоит прямо в списке `SELECT`;
- собранный `array_agg(id)` массив id родительской таблицы плюс случайный индекс `массив[floor(random() * n)::int + 1]` - надёжный способ выбрать случайного родителя для каждой строки (в отличие от `ORDER BY random() LIMIT 1` в подзапросе, который PostgreSQL может вычислить один раз на весь запрос, присвоив одинаковое значение всем строкам);
- `CROSS JOIN` (или запятая в `FROM`) - умножает число строк, например для генерации нескольких позиций заказа на один заказ;
- `ARRAY['a','b','c'][...]` - случайный выбор значения из небольшого фиксированного списка (статус заказа, город доставки);
- `ON CONFLICT DO NOTHING` - чтобы случайные повторы значений, нарушающие уникальность, не прерывали вставку ошибкой, а просто пропускались.
