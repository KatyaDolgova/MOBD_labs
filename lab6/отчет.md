## 1. Столбец JSONB для характеристик товара

У товаров разных категорий принципиально разный набор атрибутов (у электроники - объём памяти, у книг - число страниц), и описывать их фиксированными столбцами неудобно: пришлось бы либо завести десятки столбцов, большинство которых были бы `NULL` для товара не из этой категории, либо создавать отдельные таблицы под каждую категорию. `JSONB` хранит произвольный набор пар «ключ-значение» в одном столбце.

```sql
ALTER TABLE products ADD COLUMN IF NOT EXISTS attributes JSONB;

UPDATE products AS p
SET attributes = CASE c.parent_id
    WHEN 1 THEN jsonb_build_object(
        'specs', jsonb_build_object(
            'screen_inches', round((random() * 5 + 4)::numeric, 1),
            'memory_gb', (ARRAY[32, 64, 128, 256, 512])[floor(random() * 5)::int + 1]
        ),
        'color', (ARRAY['black', 'white', 'silver', 'blue'])[floor(random() * 4)::int + 1]
    )
    WHEN 2 THEN jsonb_build_object('size', ..., 'color', ..., 'material', ...)
    WHEN 3 THEN jsonb_build_object('pages', ..., 'cover', ...)
    WHEN 4 THEN jsonb_build_object('material', ..., 'weight_kg', ...)
    WHEN 5 THEN jsonb_build_object('weight_kg', ..., 'color', ...)
END
FROM categories AS c
WHERE c.id = p.category_id;
```

`c.parent_id` - это **корневая** категория товара (Электроника / Одежда / Книги / Дом и сад / Спорт), поэтому для всех  товаров характеристики заполнены по-разному, в зависимости от того, что это за товар. Для электроники характеристики сделаны **вложенными** (`specs` - отдельный JSON-объект внутри `attributes`) 

**Фрагмент результата** (по одному примеру на корневую категорию):

| parent_id | title | attributes |
|---|---|---|
| 1 | Товар №1 | `{"color": "silver", "specs": {"memory_gb": 256, "screen_inches": 6.0}}` |
| 2 | Товар №4 | `{"size": "XL", "color": "black", "material": "polyester"}` |
| 3 | Товар №15 | `{"cover": "мягкая", "pages": 395}` |
| 4 | Товар №3 | `{"material": "дерево", "weight_kg": 13.3}` |
| 5 | Товар №2 | `{"color": "red", "weight_kg": 8.1}` |

## 2. Запросы к JSONB: `->`, `->>`, `#>`, `#>>`, `@>`, `?`

### 2.1–2.2 `->` и `->>` - извлечение по ключу

```sql
SELECT title, attributes ->> 'color' AS color
FROM products
WHERE attributes ? 'color'
LIMIT 10;
```

| title | color |
|---|---|
| Товар №1 | silver |
| Товар №4 | black |
| Товар №7 | black |

`->>` возвращает значение как **текст** - поэтому `color` в выводе без кавычек, обычная строка. `->` вернул бы то же значение, но как тип `JSONB` - на экране это выглядело бы как `"silver"` с кавычками.

### 2.3 `#>` и `#>>` - извлечение **по пути** (для вложенных объектов)

```sql
SELECT
    title,
    attributes #> '{specs}'                AS specs_as_jsonb,
    attributes #>> '{specs,screen_inches}' AS screen_inches_as_text
FROM products
WHERE attributes ? 'specs'
LIMIT 5;
```

| title | specs_as_jsonb | screen_inches_as_text |
|---|---|---|
| Товар №1 | `{"memory_gb": 256, "screen_inches": 6.0}` | 6.0 |
| Товар №10 | `{"memory_gb": 128, "screen_inches": 5.2}` | 5.2 |

`{specs}` и `{specs,screen_inches}` - это массивы ключей, описывающие путь внутрь вложенной структуры: сначала зайти в `specs`, затем (во втором случае) - в `screen_inches` внутри него. Обычные `->`/`->>` умеют спускаться только на один уровень; `#>`/`#>>` нужны именно потому, что `screen_inches` лежит на **втором** уровне вложенности, а не прямо в `attributes`.

### 2.4 `@>` - проверка «документ содержит фрагмент»

```sql
SELECT title, attributes ->> 'color' AS color
FROM products
WHERE attributes @> '{"color": "black"}'
LIMIT 10;
```

 `@>` проверяет, что JSON справа - это «подмножество» JSON слева: все пары ключ-значение из правой части должны присутствовать и совпадать в левой.

### 2.5 `?` - проверка **наличия ключа** 

```sql
SELECT count(*) AS books_with_pages FROM products WHERE attributes ? 'pages';
```

`?` не смотрит, какое значение у `pages` - только то, что ключ существует.

### 2.6 Комбинация `@>` с двумя условиями сразу

```sql
SELECT title, attributes FROM products
WHERE attributes @> '{"color": "black", "size": "L"}'
LIMIT 10;
```

Оба условия проверяются одним оператором `@>`, потому что они оба - пары внутри одного фрагмента `{"color": "black", "size": "L"}`.

## 3. "Тяжёлые" запросы: планы ДО индексов (`EXPLAIN ANALYZE`)

Выбрано три запроса из предыдущих работ, разных по характеру нагрузки.

### Таблица 1 - все три запроса БЕЗ новых индексов

| № | Запрос | Что ищет | Тип сканирования | Execution Time |
|---|---|---|---|---|
| 1 | `category_id = 6 AND price < 20000` | товары категории дешевле N | `Bitmap Heap Scan` + отдельный `Filter` по `price` | 0.172 мс |
| 2 | выручка продавцов > 7 000 000 (3 JOIN + HAVING) | продавцы-лидеры | `Seq Scan` на всех трёх таблицах | 9.997 мс |
| 3 | `price = 23115.70` | точечный поиск по цене | `Seq Scan` по всей таблице | 0.330 мс |

Ниже - полные планы, по которым эта таблица собрана.

#### Запрос 1 - фильтр по двум столбцам (`category_id` + `price`)

```sql
EXPLAIN ANALYZE
SELECT title, price FROM products WHERE category_id = 6 AND price < 20000;
```

```
Bitmap Heap Scan on products  (actual time=0.058..0.148 rows=38 loops=1)
  Recheck Cond: (category_id = 6)
  Filter: (price < '20000'::numeric)
  Rows Removed by Filter: 51
  Heap Blocks: exact=31
  ->  Bitmap Index Scan on idx_products_category_id  (actual time=0.036..0.036 rows=89 loops=1)
        Index Cond: (category_id = 6)
Execution Time: 0.172 ms
```

`category_id = 6` отрабатывает через `Bitmap Index Scan` (уже создан индекс). Но условие `price < 20000` в этом плане проверяется **отдельно**, строкой `Filter`, уже после того, как 89 строк категории 6 были физически прочитаны из таблицы: `Rows Removed by Filter: 51` означает, что 51 из этих 89 строк были прочитаны зря и отброшены только на этапе `Filter`.

#### Запрос 2 - выручка продавцов выше порога (из лабы №3, `HAVING`)

```sql
EXPLAIN ANALYZE
SELECT s.id, s.store_name, SUM(oi.quantity * oi.unit_price) AS revenue
FROM sellers AS s
JOIN products AS p ON p.seller_id = s.id
JOIN order_items AS oi ON oi.product_id = p.id
GROUP BY s.id, s.store_name
HAVING SUM(oi.quantity * oi.unit_price) > 7000000;
```

```
HashAggregate  (actual time=9.849..9.866 rows=9 loops=1)
  ->  Hash Join  (actual time=4.038..7.301 rows=3001 loops=1)
        ->  Hash Join  (actual time=2.432..4.782 rows=3001 loops=1)
              ->  Seq Scan on order_items oi  (actual time=1.233..2.212 rows=3001 loops=1)
              ->  Hash  ->  Seq Scan on products p  (actual time=0.026..0.519 rows=1200 loops=1)
        ->  Hash  ->  Seq Scan on sellers s  (actual time=1.544..1.552 rows=30 loops=1)
Execution Time: 9.997 ms
```

Все три таблицы читаются **последовательно** (`Seq Scan`). Для таблиц такого размера (30, 1200 и 3001 строка) последовательное чтение **дешевле**, чем обращение к индексу для каждой строки: индекс выгоден, когда нужно выбрать **малую долю** строк, а здесь в соединении участвуют практически все строки всех трёх таблиц.

#### Запрос 3 - точечный поиск по цене

```sql
EXPLAIN ANALYZE
SELECT id, title FROM products WHERE price = 23115.70;
```

```
Seq Scan on products  (actual time=0.015..0.312 rows=1 loops=1)
  Filter: (price = 23115.70)
  Rows Removed by Filter: 1199
Execution Time: 0.330 ms
```

На `price` никакого индекса ещё не было, поэтому PostgreSQL читает **всю** таблицу  только для того, чтобы найти единственную строку, где цена совпадает.

## 4. B-tree индексы: план ПОСЛЕ

```sql
CREATE INDEX IF NOT EXISTS idx_products_cat_price ON products(category_id, price);
CREATE INDEX IF NOT EXISTS idx_products_price ON products(price);
```

### Таблица 2 - те же три запроса С новыми индексами

| № | Запрос | Тип сканирования | Execution Time |
|---|---|---|---|
| 1 | `category_id = 6 AND price < 20000` | `Bitmap Heap Scan` + `Bitmap Index Scan on idx_products_cat_price`, без `Filter` | 0.172 мс |
| 2 | выручка продавцов > 7 000 000 | `Seq Scan` на всех трёх таблицах (не изменилось) | 9.997 мс |
| 3 | `price = 23115.70` | `Index Scan using idx_products_price` | 0.144 мс |

### Таблица 3 - сравнение "Таблица 1" и "Таблица 2" (было → стало)

| № | Тип сканирования: было | Тип сканирования: стало | Время: было | Время: стало |
|---|---|---|---|---|
| 1 | `Bitmap Heap Scan` + `Filter` по `price` | `Bitmap Heap Scan`, оба условия в `Index Cond` | 0.172 мс | 0.172 мс |
| 2 | `Seq Scan` (все 3 таблицы) | `Seq Scan` (все 3 таблицы) - без изменений | 9.997 мс | 9.997 мс |
| 3 | `Seq Scan` по всей таблице | `Index Scan` по индексу | 0.330 мс | 0.144 мс |

#### Запрос 1: было → стало

```
-- БЫЛО
Filter: (price < '20000'::numeric)
Rows Removed by Filter: 51
->  Bitmap Index Scan on idx_products_category_id
      Index Cond: (category_id = 6)

-- СТАЛО
Recheck Cond: ((category_id = 6) AND (price < '20000'::numeric))
->  Bitmap Index Scan on idx_products_cat_price
      Index Cond: ((category_id = 6) AND (price < '20000'::numeric))
```

| | Проверка `price` | Heap Blocks |
|---|---|---|
| Было | отдельным `Filter`, уже после чтения строк | 31 |
| Стало | прямо в `Index Cond`, внутри самого индекса | 23 |

**Почему план изменился.** Без составного индекса по цене проверить нечем - всё, что можно получить из индекса, это 89 строк категории 6; дальнейшую проверку по цене PostgreSQL вынужден делать вручную, уже читая эти строки из таблицы (`Filter`). Новый индекс `(category_id, price)` умеет проверять **оба** условия сразу внутри себя, поэтому строка `Filter` исчезла совсем, а `Index Cond` теперь содержит оба условия. Индекс сразу вернул точные 38 нужных строк - пришлось прочитать меньше страниц таблицы (`Heap Blocks`: 31 → 23).

#### Запрос 2: почему план не изменился, хотя индексы добавлены

```sql
CREATE INDEX IF NOT EXISTS idx_products_seller_id ON products(seller_id);
CREATE INDEX IF NOT EXISTS idx_order_items_product_id ON order_items(product_id);
```

Добавила индексы для этого запроса - по `seller_id` в `products` и по `product_id` в `order_items` - и повторно сняла план. Результат:

```
HashAggregate  (actual time=2.777..2.787 rows=9 loops=1)
  ->  Hash Join  (actual time=0.430..1.615 rows=3001 loops=1)
        ->  Hash Join  (actual time=0.307..1.034 rows=3001 loops=1)
              ->  Seq Scan on order_items oi  (actual time=0.007..0.186 rows=3001 loops=1)
              ->  Hash  ->  Seq Scan on products p  (actual time=0.008..0.176 rows=1200 loops=1)
        ->  Hash  ->  Seq Scan on sellers s  (actual time=0.036..0.038 rows=30 loops=1)
Execution Time: 3.199 ms
```

Тип сканирования **не изменился**: все три таблицы читаются `Seq Scan`, индексы не задействованы ни на одном из узлов плана - так же, как и до их добавления. Причина не в отсутствии подходящего индекса, а в объёме данных: для таблиц такого малого размера (30–3000 строк) PostgreSQL сам решает, что `Seq Scan` дешевле, чем обращение к индексу по каждой из почти всех строк таблицы, участвующих в соединении.

#### Запрос 3: было → стало

```
-- БЫЛО
Seq Scan on products
  Filter: (price = 23115.70)
  Rows Removed by Filter: 1199

-- СТАЛО
Index Scan using idx_products_price on products
  Index Cond: (price = 23115.70)
```

| | Строк прочитано |
|---|---|
| Было | 1200 (1199 отброшено) |
| Стало | 1 (сразу нужная) |

**Почему план изменился.** Условие `price = 23115.70` выбирает ровно одну строку из 1200. До индекса PostgreSQL не мог быстро найти эту строку иначе, чем прочитав всё подряд. После создания `idx_products_price` тип узла сменился с `Seq Scan` прямо на `Index Scan`: индекс напрямую указывает, где лежит нужная строка, и таблица читается только в этом одном месте. Время выполнения снизилось больше чем в 2 раза

## 5. GIN-индекс для JSONB

B-tree (индексы из пункта 4) сравнивает значение столбца **целиком**, а `@>` проверяет «есть ли внутри JSON-документа такой-то фрагмент» - для этого нужен другой тип индекса, **GIN** (Generalized Inverted Index): он раскладывает JSON на отдельные ключи/значения и хранит для каждого список строк, где он встречается.

```sql
CREATE INDEX IF NOT EXISTS idx_products_attrs ON products USING GIN (attributes);
ANALYZE products;
```

Проверила один и тот же оператор `@>` на двух запросах с разной избирательностью:

### Таблица 4 - сравнение двух вариантов после создания индекса

| Вариант | Запрос | Доля строк | Тип сканирования | Execution Time |
|---|---|---|---|---|
| А | `@> '{"color": "black"}'` | 170 / 1200 ≈ 14% | `Seq Scan` - индекс **не использован** | 0.521 мс |
| Б | `@> '{"color": "black", "size": "L"}'` | 13 / 1200 ≈ 1% | `Bitmap Heap Scan` + `Bitmap Index Scan on idx_products_attrs` - индекс **использован сам** | 0.245 мс |

### Вариант А - индекс существует, но не используется

```sql
EXPLAIN ANALYZE SELECT title FROM products WHERE attributes @> '{"color": "black"}';
```

```
Seq Scan on products  (actual time=0.072..0.578 rows=170 loops=1)
  Filter: (attributes @> '{"color": "black"}'::jsonb)
  Rows Removed by Filter: 1030
Execution Time: 0.521 ms
```

Та же причина, что у Запроса 2 (пункт 4): 170 строк из 1200 (≈14%) - недостаточно избирательно.

### Вариант Б - индекс используется сам, без подсказок

```sql
EXPLAIN ANALYZE SELECT title FROM products WHERE attributes @> '{"color": "black", "size": "L"}';
```

```
Bitmap Heap Scan on products  (actual time=0.168..0.191 rows=13 loops=1)
  Recheck Cond: (attributes @> '{"size": "L", "color": "black"}'::jsonb)
  Heap Blocks: exact=11
  ->  Bitmap Index Scan on idx_products_attrs  (actual time=0.135..0.136 rows=13 loops=1)
        Index Cond: (attributes @> '{"size": "L", "color": "black"}'::jsonb)
Execution Time: 0.245 ms
```

При более узком условии (13 строк из 1200, ≈1%) планировщик сам переключился на `Bitmap Index Scan`. Вывод: планировщик использует GIN-индекс тогда, когда это выгодно - зависит не от наличия индекса, а от избирательности конкретного условия.

## 6. Обратная сторона индексов: цена на вставке

Индексы ускоряют чтение, но каждый `INSERT` должен обновить **все** индексы таблицы, а не только добавить строку в неё саму - это стоит дополнительного времени. Чтобы показать эффект, созданы две временные таблицы одинаковой структуры: у одной нет ни одного дополнительного индекса, у другой - пять (`category_id`, `seller_id`, `price`, составной `(category_id, price)`, `title`).

```sql
\timing on
INSERT INTO perf_no_index (...)   SELECT ... FROM generate_series(1, 50000) ...;
INSERT INTO perf_with_index (...) SELECT ... FROM generate_series(1, 50000) ...;
```

**Реальный результат замера** (50 000 строк в каждую таблицу):

| Таблица | Индексов сверх первичного ключа | Время вставки |
|---|---|---|
| `perf_no_index` | 0 | **434 мс** |
| `perf_with_index` | 5 | **1750 мс** |

Вставка в таблицу с пятью индексами заняла **в 4 раза дольше**. Разница - это и есть "цена" индексов: при каждой вставленной строке PostgreSQL должен также вставить соответствующую запись в B-tree-структуру каждого из пяти индексов, то есть по сути проделать до шести операций вставки вместо одной.

## 7. Обоснование выбранных индексов

| Индекс | Зачем добавлен | Подтверждение по плану |
|---|---|---|
| `idx_products_cat_price (category_id, price)` | Запрос 1 фильтрует одновременно по категории и диапазону цены | `Filter` исчез, оба условия ушли в `Index Cond`, число прочитанных блоков снизилось |
| `idx_products_price (price)` | Точечный поиск по цене (`price = ...`, Запрос 3) читал всю таблицу ради одной строки | `Seq Scan` → `Index Scan`, `Rows Removed by Filter: 1199` исчезло |
| `idx_products_attrs USING GIN (attributes)` | Единственный способ эффективно искать по вхождению фрагмента JSONB (`@>`, Запрос 4) - B-tree для этого не подходит в принципе | При достаточно избирательном условии планировщик сам выбрал `Bitmap Index Scan` по этому индексу |
| `idx_products_seller_id (seller_id)`, `idx_order_items_product_id (product_id)` | Проверочная попытка для Запроса 2 (выручка продавцов) -  чтобы убедиться | Плана это **не изменило** - все три таблицы остались на `Seq Scan` |

**Общий принцип выбора**: индекс имеет смысл добавлять только под конкретный частый запрос с **высокой избирательностью** условия (малая доля строк от общего объёма таблицы), и обязательно сверять решение с планом `EXPLAIN ANALYZE`.
