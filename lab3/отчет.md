# Лабораторная работа №3. Многотабличные запросы и аналитические представления

Все запросы выполнены на базе `marketplace`, наполненной в лабораторной работе №2: 200 пользователей, 30 продавцов, 20 категорий (5 корневых + 15 подкатегорий), 1200 товаров, 1000 заказов, ~3000 позиций заказов и т. д. 

---

## 1. INNER JOIN не менее трёх таблиц

**Назначение.** Показать карточку товара сразу с названием его категории и именем магазина-продавца - три таблицы, соединённые по внешним ключам.

```sql
SELECT
    p.id,
    p.title,
    c.name       AS category,
    s.store_name AS seller
FROM products AS p
JOIN categories AS c ON c.id = p.category_id
JOIN sellers   AS s ON s.id = p.seller_id
ORDER BY p.id
LIMIT 10;
```

| id | title | category | seller |
|---|---|---|---|
| 1 | Товар №1 | Электроника / Подкатегория 1 | Магазин №5 |
| 2 | Товар №2 | Спорт / Подкатегория 3 | Магазин №19 |
| 3 | Товар №3 | Дом и сад / Подкатегория 1 | Магазин №25 |
| 4 | Товар №4 | Одежда / Подкатегория 3 | Магазин №1 |
| 5 | Товар №5 | Дом и сад / Подкатегория 1 | Магазин №6 |

Каждый `JOIN` соединяет пару таблиц по условию `ON`: `c.id = p.category_id` связывает товар с его категорией, `s.id = p.seller_id` - с продавцом. `INNER JOIN` (здесь просто `JOIN`) оставляет только те строки, для которых соответствие нашлось в обеих таблицах; товар без категории или без продавца (что в нашей схеме невозможно - оба поля `NOT NULL`) в результат не попал бы.

## 2. LEFT JOIN: строки без соответствия

**Назначение.** Найти товары, на которые ещё нет ни одного отзыва.

```sql
SELECT
    p.id,
    p.title
FROM products AS p
LEFT JOIN reviews AS r ON r.product_id = p.id
WHERE r.id IS NULL
ORDER BY p.id
LIMIT 10;
```

| id | title |
|---|---|
| 2 | Товар №2 |
| 3 | Товар №3 |
| 6 | Товар №6 |
| 12 | Товар №12 |
| 15 | Товар №15 |

Всего таких товаров - **687** из 1200. `LEFT JOIN` сохраняет все строки `products`, даже те, для которых нет пары в `reviews`: у них столбец `r.id` становится `NULL`. Условие `WHERE r.id IS NULL` отбирает именно эти строки - товары без единого отзыва. Обычный `JOIN` вместо `LEFT JOIN` выкинул бы такие товары из результата ещё до того, как до них дошла бы фильтрация.

## 3. Группировка и агрегация

**Назначение.** По каждой категории - количество товаров в ней и средняя цена.

```sql
SELECT
    c.name                      AS category,
    COUNT(*)                    AS products_count,
    AVG(p.price)::numeric(12,2) AS avg_price
FROM products AS p
JOIN categories AS c ON c.id = p.category_id
GROUP BY c.name
ORDER BY products_count DESC;
```

| category | products_count | avg_price |
|---|---|---|
| Дом и сад / Подкатегория 1 | 93 | 21703.24 |
| Одежда / Подкатегория 3 | 92 | 27064.65 |
| Электроника / Подкатегория 1 | 89 | 24197.88 |
| Одежда / Подкатегория 1 | 85 | 26971.46 |
| Электроника / Подкатегория 3 | 80 | 24286.03 |
| … | … | … |
| Спорт / Подкатегория 3 | 67 | 25241.92 |

(15 строк всего - ровно по одной на каждую подкатегорию.)

`GROUP BY c.name` делит все строки на группы - по одной группе на каждое уникальное название категории. Для каждой группы `COUNT(*)` считает число строк (товаров) в ней, а `AVG(p.price)` - среднюю цену внутри группы. В списке `SELECT` при группировке допустимы только столбцы из `GROUP BY` (здесь `c.name`) и агрегатные функции - выбрать, например, `p.title` без агрегирования было бы ошибкой: для группы из 93 строк у `title` нет одного значения.

## 4. HAVING: фильтрация групп

**Назначение.** Продавцы, чья суммарная выручка (по проданным позициям заказов) превышает 7 000 000.

```sql
SELECT
    s.id,
    s.store_name,
    SUM(oi.quantity * oi.unit_price) AS revenue
FROM sellers AS s
JOIN products AS p     ON p.seller_id = s.id
JOIN order_items AS oi ON oi.product_id = p.id
GROUP BY s.id, s.store_name
HAVING SUM(oi.quantity * oi.unit_price) > 7000000
ORDER BY revenue DESC;
```

| id | store_name | revenue |
|---|---|---|
| 3 | Магазин №3 | 9324168.38 |
| 5 | Магазин №5 | 8952576.05 |
| 9 | Магазин №9 | 8738488.99 |
| 28 | Магазин №28 | 8640418.45 |
| 23 | Магазин №23 | 8628245.86 |
| 16 | Магазин №16 | 8376604.11 |
| 25 | Магазин №25 | 8008122.87 |
| 7 | Магазин №7 | 7654487.48 |
| 6 | Магазин №6 | 7555100.53 |

9 продавцов из 30 превысили порог. `WHERE` здесь использовать нельзя: `WHERE` фильтрует исходные строки `order_items`/`products` **до** группировки, а на этом этапе ещё не существует значения `SUM(...)` - оно появляется только после `GROUP BY`. `HAVING` фильтрует уже готовые группы по результату агрегатной функции, поэтому выполняется позже `WHERE`.

## 5. Подзапросы: скалярный, IN, EXISTS

### 5.1 Скалярный подзапрос

**Назначение.** Товары дороже средней цены по всей базе.

```sql
SELECT id, title, price
FROM products
WHERE price > (SELECT AVG(price) FROM products)
ORDER BY price
LIMIT 10;
```

| id | title | price |
|---|---|---|
| 201 | Товар №201 | 24691.36 |
| 374 | Товар №374 | 24929.62 |
| 379 | Товар №379 | 24941.89 |
| 1099 | Товар №1099 | 25016.80 |
| 755 | Товар №755 | 25196.82 |

Подзапрос `(SELECT AVG(price) FROM products)` возвращает **ровно одно** число - среднюю цену по всем 1200 товарам, - поэтому его можно подставить прямо в условие сравнения, как если бы это было обычное число. Такой подзапрос называется скалярным.

### 5.2 Подзапрос с IN

**Назначение.** Продавцы, у которых есть хотя бы один активный товар.

```sql
SELECT id, store_name
FROM sellers
WHERE id IN (SELECT seller_id FROM products WHERE is_active = TRUE)
ORDER BY id
LIMIT 10;
```

| id | store_name |
|---|---|
| 1 | Магазин №1 |
| 2 | Магазин №2 |
| 3 | Магазин №3 |
| 4 | Магазин №4 |
| 5 | Магазин №5 |

Подзапрос `(SELECT seller_id FROM products WHERE is_active = TRUE)` возвращает **множество** значений `seller_id` (у активных товаров могут повторяться продавцы). `IN` проверяет, входит ли `id` текущего продавца в это множество.

### 5.3 Подзапрос с EXISTS (коррелированный)

**Назначение.** Продавцы, у которых есть хотя бы один товар (аналог предыдущего запроса, но через `EXISTS`).

```sql
SELECT s.id, s.store_name
FROM sellers AS s
WHERE EXISTS (SELECT 1 FROM products AS p WHERE p.seller_id = s.id)
ORDER BY s.id
LIMIT 10;
```

| id | store_name |
|---|---|
| 1 | Магазин №1 |
| 2 | Магазин №2 |
| 3 | Магазин №3 |
| 4 | Магазин №4 |
| 5 | Магазин №5 |

Это **коррелированный** подзапрос: внутри него есть ссылка `p.seller_id = s.id` на `s` из внешнего запроса. Логически подзапрос выполняется заново для каждой строки `sellers` и проверяет: «нашлась ли хотя бы одна строка в `products` с этим `seller_id`?». `EXISTS` возвращает `TRUE`, как только находит первую подходящую строку, не считая их все - поэтому часто эффективнее, чем `IN` на больших таблицах.

## 6. CTE (WITH) и рекурсивный CTE

### 6.1 Обычный CTE - разбиение сложного запроса на шаги

**Назначение.** Доля выручки каждого продавца в общей выручке маркетплейса.

```sql
WITH seller_rev AS (
    SELECT p.seller_id, SUM(oi.quantity * oi.unit_price) AS revenue
    FROM products AS p
    JOIN order_items AS oi ON oi.product_id = p.id
    GROUP BY p.seller_id
)
SELECT
    s.store_name,
    r.revenue,
    round(r.revenue / (SELECT SUM(revenue) FROM seller_rev) * 100, 2) AS share_percent
FROM seller_rev AS r
JOIN sellers AS s ON s.id = r.seller_id
ORDER BY r.revenue DESC
LIMIT 10;
```

| store_name | revenue | share_percent |
|---|---|---|
| Магазин №3 | 9324168.38 | 4.99 |
| Магазин №5 | 8952576.05 | 4.79 |
| Магазин №9 | 8738488.99 | 4.67 |
| Магазин №28 | 8640418.45 | 4.62 |
| Магазин №23 | 8628245.86 | 4.62 |

Запрос разбит на два логических шага: `WITH seller_rev AS (...)` сначала считает выручку каждого продавца (это было бы первым отдельным запросом), а основная часть использует этот промежуточный результат как обычную таблицу - присоединяет к нему названия магазинов и считает долю каждого в общей сумме.

Доля считается через **скалярный подзапрос** `(SELECT SUM(revenue) FROM seller_rev)`  он возвращает ровно одно число (суммарную выручку всех продавцов) и не зависит от текущей строки, поэтому вычисляется один раз и подставляется как обычное число в каждой строке результата. .

Без CTE пришлось бы либо повторить вычисление выручки по продавцам два раза, либо вложить один запрос в другой, что читалось бы намного хуже.

### 6.2 Рекурсивный CTE - обход дерева категорий

**Назначение.** Получить все категории (и корневые, и подкатегории) с указанием их уровня в дереве.

```sql
WITH RECURSIVE category_tree AS (
    -- базовый случай: корневые категории
    SELECT id, parent_id, name, 1 AS level
    FROM categories
    WHERE parent_id IS NULL

    UNION ALL

    -- рекурсивный случай: дети текущего уровня
    SELECT c.id, c.parent_id, c.name, ct.level + 1
    FROM categories AS c
    JOIN category_tree AS ct ON c.parent_id = ct.id
)
SELECT level, id, parent_id, name
FROM category_tree
ORDER BY level, id;
```

| level | id | parent_id | name |
|---|---|---|---|
| 1 | 1 | - | Электроника |
| 1 | 2 | - | Одежда |
| 1 | 3 | - | Книги |
| 1 | 4 | - | Дом и сад |
| 1 | 5 | - | Спорт |
| 2 | 6 | 1 | Электроника / Подкатегория 1 |
| 2 | 7 | 2 | Одежда / Подкатегория 1 |
| 2 | 8 | 3 | Книги / Подкатегория 1 |
| … | … | … | … |

Всего 20 строк - 5 корневых плюс 15 подкатегорий.

`WITH RECURSIVE` состоит из двух частей, соединённых `UNION ALL`:
1. **Базовый случай** - стартовые строки (здесь: категории без родителя, `level = 1`).
2. **Рекурсивный случай** - присоединяет к каждой строке предыдущего шага (`category_tree`, здесь через псевдоним `ct`) её детей (`c.parent_id = ct.id`), увеличивая `level` на 1.

PostgreSQL выполняет это как цикл: сначала в `category_tree` попадают 5 корневых категорий, затем на основе них находятся их 15 подкатегорий (`level = 2`), затем PostgreSQL пытается найти детей **этих** строк - таких не находится, рекурсия останавливается сама. В нашей схеме дерево категорий состоит ровно из двух уровней, но тот же запрос без изменений обработал бы дерево любой глубины.

## 7. Представления (VIEW)

### VIEW 1. seller_revenue

**Назначение.** Готовая витрина выручки по продавцам, чтобы не повторять `JOIN` + `GROUP BY` в каждом отчёте.

```sql
CREATE VIEW seller_revenue AS
SELECT
    s.id,
    s.store_name AS name,
    SUM(oi.quantity * oi.unit_price) AS revenue
FROM sellers AS s
JOIN products AS p     ON p.seller_id = s.id
JOIN order_items AS oi ON oi.product_id = p.id
GROUP BY s.id, s.store_name;
```

Обращение к представлению - как к обычной таблице:

```sql
SELECT * FROM seller_revenue ORDER BY revenue DESC LIMIT 10;
```

| id | name | revenue |
|---|---|---|
| 3 | Магазин №3 | 9324168.38 |
| 5 | Магазин №5 | 8952576.05 |
| 9 | Магазин №9 | 8738488.99 |

### VIEW 2. category_stats

**Назначение.** Витрина ассортимента: количество товаров и средняя цена по каждой категории, включая категории, в которых товаров пока нет (`LEFT JOIN` вместо обычного `JOIN`).

```sql
CREATE VIEW category_stats AS
SELECT
    c.id,
    c.name,
    COUNT(p.id)                  AS products_count,
    AVG(p.price)::numeric(12,2)  AS avg_price
FROM categories AS c
LEFT JOIN products AS p ON p.category_id = c.id
GROUP BY c.id, c.name;
```

```sql
SELECT * FROM category_stats ORDER BY products_count DESC;
```

| id | name | products_count | avg_price |
|---|---|---|---|
| 9 | Дом и сад / Подкатегория 1 | 93 | 21703.24 |
| 17 | Одежда / Подкатегория 3 | 92 | 27064.65 |
| … | … | … | … |
| 4 | Дом и сад | 0 | - |
| 2 | Одежда | 0 | - |
| 1 | Электроника | 0 | - |

Последние 5 строк - корневые категории: в них самих товаров нет (товары лежат только в подкатегориях), поэтому `products_count = 0`, а `avg_price` - `NULL` (у `AVG` нет ни одного значения, чтобы усреднить). Если бы вместо `LEFT JOIN` стоял обычный `JOIN`, эти 5 строк вообще не попали бы в представление - `category_stats` - наглядный пример того, зачем в аналитических витринах нужен именно `LEFT JOIN`.

**Отличие от обычной таблицы.** `seller_revenue` и `category_stats` **не хранят** данных - это сохранённые запросы. Каждое обращение к ним (`SELECT * FROM seller_revenue`) заново выполняет лежащий в основе `SELECT` и возвращает актуальные данные на этот момент. Если добавить новый заказ, в `seller_revenue` сразу появятся его деньги - без какого-либо `REFRESH` или пересчёта. Это отличает обычный `VIEW` от `MATERIALIZED VIEW`, который физически хранит результат и обновляется только по команде `REFRESH MATERIALIZED VIEW`.

## Контрольные вопросы

### 1. Что такое соединение таблиц и по какому условию оно обычно выполняется?

Соединение (`JOIN`) объединяет строки двух таблиц в одну по условию, заданному в секции `ON`. Чаще всего это условие - равенство внешнего ключа одной таблицы первичному ключу другой, например `c.id = p.category_id`: так строки `products` «находят» свою строку `categories`. Если столбцы соединения называются одинаково в обеих таблицах, можно использовать сокращённую запись `USING (имя_столбца)`.

### 2. Чем INNER JOIN отличается от LEFT JOIN? Приведите пример, где нужен именно LEFT JOIN.

`INNER JOIN` (обычный `JOIN`) оставляет только те строки, для которых условие `ON` нашло соответствие в обеих таблицах; строки без пары отбрасываются целиком. `LEFT JOIN` сохраняет **все** строки левой таблицы независимо от того, нашлась пара справа или нет - если не нашлась, столбцы из правой таблицы заполняются `NULL`.

Пример, где нужен именно `LEFT JOIN`: пункт 2 этого отчёта - поиск товаров без отзывов. Если использовать `INNER JOIN products ... reviews`, товары без единого отзыва вообще не попадут в результат (ведь для них нет пары в `reviews`), и найти их будет невозможно. Только `LEFT JOIN` + `WHERE r.id IS NULL` показывает именно отсутствие соответствия.

### 3. Какие агрегатные функции вы знаете? В чём различие между COUNT(*) и COUNT(столбец)?

Основные агрегатные функции: `COUNT` (количество), `SUM` (сумма), `AVG` (среднее), `MIN` и `MAX` (наименьшее и наибольшее значение).

`COUNT(*)` считает **все строки** группы, независимо от того, есть ли в них `NULL`. `COUNT(столбец)` считает только те строки, где значение этого столбца **не `NULL`** - строки с `NULL` в этом столбце пропускаются. Например, `COUNT(apartment)` в таблице `addresses` даст число меньше, чем `COUNT(*)`, если у части адресов квартира не указана.

### 4. Для чего предназначена секция GROUP BY и что допустимо в списке выборки при группировке?

`GROUP BY` делит строки результата на группы по значениям перечисленных столбцов - у всех строк внутри одной группы совпадают значения этих столбцов. Для каждой группы агрегатные функции (`COUNT`, `SUM`, `AVG`…) возвращают одно сводное значение.

В списке `SELECT` при группировке допустимы только:
- столбцы, перечисленные в `GROUP BY` (у них одно значение на группу, это однозначно);
- агрегатные функции (они сводят много строк в одно значение).

Любой другой столбец вставить нельзя: у него внутри группы может быть несколько разных значений, и непонятно, какое из них показать.

### 5. В чём различие между WHERE и HAVING и в каком порядке они выполняются?

`WHERE` фильтрует **исходные строки до группировки** - он не видит результатов агрегатных функций, потому что на этом этапе группы ещё не сформированы. `HAVING` фильтрует уже **готовые группы**, после того как агрегатные функции посчитаны, - поэтому в условии `HAVING` можно использовать `SUM(...)`, `COUNT(...)` и т. п., а в `WHERE` - нельзя.

Порядок выполнения: `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`. То есть `WHERE` отрабатывает раньше группировки, а `HAVING` - уже после неё. Пример из пункта 4 отчёта: нельзя написать `WHERE SUM(...) > 7000000`, потому что до группировки никакой суммы ещё не существует.

### 6. Что такое подзапрос? Чем коррелированный подзапрос отличается от некоррелированного?

Подзапрос - запрос, вложенный внутрь другого запроса (в список `SELECT`, в условие `WHERE`, или вместо таблицы в `FROM`). Скалярный подзапрос возвращает одно значение, подзапрос в `IN`/`EXISTS` - множество строк.

**Некоррелированный** подзапрос не ссылается ни на одну таблицу внешнего запроса - он вычисляется один раз, независимо от того, какая строка внешнего запроса сейчас обрабатывается. Пример: `(SELECT AVG(price) FROM products)` в пункте 5.1 - число не зависит от конкретного товара снаружи.

**Коррелированный** подзапрос содержит ссылку на столбец внешнего запроса (например, `p.seller_id = s.id` в пункте 5.3) и логически выполняется заново **для каждой строки** внешнего запроса - как если бы это был маленький запрос внутри цикла по строкам. Он мощнее (может проверять что-то индивидуально для каждой строки), но потенциально дороже по производительности.

### 7. Как работает предикат EXISTS и когда его удобно применять?

`EXISTS (подзапрос)` возвращает `TRUE`, если подзапрос вернул **хотя бы одну строку**, и `FALSE`, если не вернул ни одной. Самого содержимого найденных строк не важно - значения не используются, важен только факт их существования. Как только находится первая подходящая строка, PostgreSQL может прекратить поиск, не проверяя остальные - это часто делает `EXISTS` эффективнее, чем `IN` с большим подзапросом.

Удобно применять, когда нужно проверить «есть ли у этой строки хотя бы одна связанная запись» - например, «есть ли у продавца хотя бы один товар» (пункт 5.3) или «есть ли у заказа хотя бы одна позиция». `NOT EXISTS` - симметричная проверка отсутствия.

### 8. Что такое общее табличное выражение (CTE) и для чего нужен рекурсивный CTE?

CTE (`WITH имя AS (запрос)`) - именованный промежуточный результат, доступный в основном запросе как обычная таблица. Он не меняет итоговый результат (то же самое можно написать через подзапросы), но делает сложный запрос **читаемым**, разбивая его на именованные логические шаги - как в пункте 6.1, где сначала считается выручка продавцов, а потом отдельно - её доля.

Рекурсивный CTE (`WITH RECURSIVE`) ссылается сам на себя и используется для обхода **иерархических структур** произвольной глубины - деревьев, где заранее неизвестно, сколько уровней вложенности. В пункте 6.2 он проходит дерево категорий: начинает с корней, затем на каждом шаге находит детей строк предыдущего шага, и останавливается сам, когда детей больше не находится.

### 9. Что такое представление (VIEW)? Хранит ли обычное представление данные?

`VIEW` - это сохранённый в базе `SELECT`-запрос, которому дано имя. **Обычное представление не хранит данные** - при каждом обращении к нему (`SELECT * FROM seller_revenue`) PostgreSQL заново выполняет лежащий внутри запрос и возвращает актуальный на этот момент результат. Представления используются, чтобы скрыть сложность запроса за простым именем, предоставить готовую аналитическую витрину или ограничить доступ к части столбцов исходных таблиц.

### 10. Чем материализованное представление отличается от обычного?

`MATERIALIZED VIEW`, в отличие от обычного `VIEW`, **физически хранит** результат запроса на диске, как обычная таблица. Он не пересчитывается автоматически при каждом обращении - данные обновляются только явной командой `REFRESH MATERIALIZED VIEW`. Это ускоряет чтение дорогих агрегатов (не нужно каждый раз пересчитывать `JOIN` и `GROUP BY` по всей базе), но ценой того, что данные в представлении могут быть неактуальны - отражать состояние базы на момент последнего `REFRESH`, а не текущее.
