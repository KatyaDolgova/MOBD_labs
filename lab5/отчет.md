## 1. Демонстрация транзакции: COMMIT и ROLLBACK

Показать на реальных данных, что `COMMIT` сохраняет все изменения транзакции, а `ROLLBACK` отменяет их полностью - свойство атомарности.

### Сценарий 1 - успешная транзакция

```sql
BEGIN;

INSERT INTO orders (user_id, status)
VALUES (1, 'created')
RETURNING id AS new_order_id \gset s1_

INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (:s1_new_order_id, 2, 1, 34214.08);

UPDATE stock SET quantity = quantity - 1 WHERE product_id = 2;

COMMIT;
```

| Срез | orders_count | stock.quantity (товар 2) |
|---|---|---|
| До | 1000 | 66 |
| После COMMIT | **1001** | **65** |

Все три команды внутри `BEGIN ... COMMIT` выполнились как единое целое: заказ создан, позиция добавлена, остаток уменьшен - и всё это зафиксировано одним `COMMIT`.

### Сценарий 2 - транзакция с намеренной ошибкой

```sql
BEGIN;

INSERT INTO orders (user_id, status)
VALUES (1, 'created')
RETURNING id AS new_order_id \gset s2_

INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (:s2_new_order_id, 3, 5, 25679.65);

UPDATE stock SET quantity = quantity - 999999 WHERE product_id = 3;

ROLLBACK;
```

Реальный вывод psql:

```
BEGIN
INSERT 0 1
INSERT 0 1
ОШИБКА:  новая строка в отношении "stock" нарушает ограничение-проверку "stock_quantity_check"
ПОДРОБНОСТИ:  Ошибочная строка содержит (3, -999826, ...).
ROLLBACK
```

| Срез | orders_count | stock.quantity (товар 3) |
|---|---|---|
| До сценария 2 | 1001 | 173 |
| После ROLLBACK | **1001** | **173** |

Несмотря на то, что `INSERT INTO orders` и `INSERT INTO order_items` выполнились без ошибок (видно по "INSERT 0 1" в выводе), ни один из них не сохранился в базе - `orders_count` остался 1001, а не 1002. Ошибка в третьей команде (`UPDATE stock`, нарушение `CHECK (quantity >= 0)`) перевела всю транзакцию в состояние "aborted", и `ROLLBACK` отменил **все** изменения транзакции целиком, включая те, что выполнились раньше без ошибок. Это и есть атомарность: либо применяются все изменения транзакции, либо ни одно.

## 2. Функция place_order: атомарное оформление заказа

Функция на PL/pgSQL, которая создаёт заказ, его позицию и уменьшает остаток на складе одним вызовом; при нехватке товара - исключение без частичных изменений.

```sql
CREATE OR REPLACE FUNCTION place_order(p_user BIGINT, p_product BIGINT, p_qty INT)
RETURNS BIGINT AS $$
DECLARE
    v_order_id BIGINT;
    v_price    NUMERIC(12,2);
    v_stock    INT;
BEGIN
    SELECT price INTO v_price FROM products WHERE id = p_product;
    IF v_price IS NULL THEN
        RAISE EXCEPTION 'Товар с id=% не найден', p_product;
    END IF;

    SELECT quantity INTO v_stock FROM stock WHERE product_id = p_product;
    IF v_stock IS NULL OR v_stock < p_qty THEN
        RAISE EXCEPTION 'Недостаточно товара на складе (id=%, в наличии %, запрошено %)',
            p_product, COALESCE(v_stock, 0), p_qty;
    END IF;

    INSERT INTO orders (user_id, status)
    VALUES (p_user, 'created')
    RETURNING id INTO v_order_id;

    INSERT INTO order_items (order_id, product_id, quantity, unit_price)
    VALUES (v_order_id, p_product, p_qty, v_price);

    UPDATE stock SET quantity = quantity - p_qty WHERE product_id = p_product;
    UPDATE orders SET total_amount = v_price * p_qty WHERE id = v_order_id;

    RETURN v_order_id;
END;
$$ LANGUAGE plpgsql;
```

### Успешный вызов

```sql
SELECT place_order(1, 4, 2) AS order_id;
```

| order_id |
|---|
| 1003 |

```sql
SELECT id, user_id, status, total_amount FROM orders WHERE id = 1003;
```

| id | user_id | status | total_amount |
|---|---|---|---|
| 1003 | 1 | created | 29799.64 |

Остаток товара 4 уменьшился с 95 до 93 (заказано 2 штуки).

### Вызов с нехваткой товара

```sql
SELECT place_order(1, 4, 999999);
```

```
ОШИБКА:  Недостаточно товара на складе (id=4, в наличии 93, запрошено 999999)
```

После этой ошибки проверка показала: `count(*) FROM orders` не изменился (остался 1002 - на момент этого вызова, до него успешный `place_order` уже увеличил счётчик до 1002), а `stock.quantity` для товара 4 остался 93. Ни заказ, ни позиция не были созданы - вызов функции **полностью атомарен**: PostgreSQL выполняет вызов функции как одну операцию, и исключение внутри него откатывает все изменения, сделанные функцией до точки ошибки, даже без явного `BEGIN/COMMIT` вокруг вызова - потому что сам вызов и есть одна неявная транзакция.

## 3. Функция seller_revenue: сводный показатель

Функция, возвращающая выручку конкретного продавца за заданный период - демонстрация локальной переменной и запроса с `SELECT ... INTO` внутри функции.

```sql
CREATE OR REPLACE FUNCTION seller_revenue(p_seller_id BIGINT, p_from DATE, p_to DATE)
RETURNS NUMERIC(14,2) AS $$
DECLARE
    v_revenue NUMERIC(14,2);
BEGIN
    SELECT COALESCE(SUM(oi.quantity * oi.unit_price), 0)
      INTO v_revenue
    FROM order_items AS oi
    JOIN products AS p ON p.id = oi.product_id
    JOIN orders   AS o ON o.id = oi.order_id
    WHERE p.seller_id = p_seller_id
      AND o.created_at::date BETWEEN p_from AND p_to;

    RETURN v_revenue;
END;
$$ LANGUAGE plpgsql;
```

```sql
SELECT seller_revenue(3, '2026-01-01', '2026-12-31');
```

| revenue |
|---|
| 9324168.38 |

```sql
SELECT seller_revenue(3, '2000-01-01', '2000-12-31');
```

| revenue |
|---|
| 0.00 |

Для периода, в котором у продавца не было продаж, функция вернула `0.00`, а не `NULL` - благодаря `COALESCE` внутри запроса: `SUM(...)` по пустому набору строк дал бы `NULL`, а `COALESCE(NULL, 0)` заменяет его на ноль.

## 4. Триггер аудита изменения цены

При любом изменении `products.price` старое и новое значение автоматически попадают в журнал `price_audit`, без участия приложения.

```sql
CREATE OR REPLACE FUNCTION log_price_change()
RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO price_audit (product_id, old_price, new_price)
    VALUES (OLD.id, OLD.price, NEW.price);
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_price_audit
AFTER UPDATE ON products
FOR EACH ROW
WHEN (OLD.price IS DISTINCT FROM NEW.price)
EXECUTE FUNCTION log_price_change();
```

### Проверка: изменение цены

```sql
UPDATE products SET price = price + 500 WHERE id = 10;
SELECT * FROM price_audit WHERE product_id = 10;
```

| id | product_id | old_price | new_price | changed_at |
|---|---|---|---|---|
| 1 | 10 | 26138.51 | 26638.51 | 2026-11-03 23:02:38+03 |

### Проверка: изменение ДРУГОГО столбца не создаёт запись

```sql
UPDATE products SET description = 'тест аудита, цена не менялась' WHERE id = 10;
SELECT count(*) FROM price_audit WHERE product_id = 10;
```

| count |
|---|
| 1 |

Число строк в журнале не изменилось - именно для этого в триггере стоит условие `WHEN (OLD.price IS DISTINCT FROM NEW.price)`: оно проверяется PostgreSQL **до** вызова триггерной функции, и если цена не менялась, функция `log_price_change()` вообще не вызывается. `IS DISTINCT FROM`, а не `<>`, использован потому, что обычное неравенство с `NULL` даёт `UNKNOWN` и могло бы пропустить случай, когда цена меняется с/на `NULL`.

## 5. Триггер пересчёта рейтинга товара

Поддерживать поле `products.rating` - средний балл отзывов - автоматически при добавлении нового отзыва.

```sql
CREATE OR REPLACE FUNCTION refresh_product_rating()
RETURNS TRIGGER AS $$
BEGIN
    UPDATE products
    SET rating = (
        SELECT round(AVG(score), 2)
        FROM reviews
        WHERE product_id = NEW.product_id
    )
    WHERE id = NEW.product_id;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_refresh_rating
AFTER INSERT ON reviews
FOR EACH ROW
EXECUTE FUNCTION refresh_product_rating();
```

### Проверка на товаре без единого отзыва (id = 2)

```sql
INSERT INTO reviews (user_id, product_id, score, comment) VALUES (1, 2, 4, 'Тестовый отзыв');
SELECT id, rating FROM products WHERE id = 2;
```

| id | rating |
|---|---|
| 2 | 4.00 |

```sql
INSERT INTO reviews (user_id, product_id, score, comment) VALUES (2, 2, 2, 'Второй тестовый отзыв');
SELECT id, rating FROM products WHERE id = 2;
```

| id | rating |
|---|---|
| 2 | 3.00 |

После первого отзыва (оценка 4) рейтинг стал 4.00. После второго отзыва (оценка 2) рейтинг пересчитался на среднее двух оценок: `(4 + 2) / 2 = 3.00`. Каждый `INSERT` в `reviews` заново запускает триггер, который берёт **все** отзывы товара на этот момент и пересчитывает среднее.

## 6. Где уместна логика в БД, а где - в приложении

В этой лабораторной серверная логика (функции и триггеры) использована для задач, связанных с целостностью данных:

- **place_order** - атомарность оформления заказа. Если бы эту проверку сделали в приложении (сначала проверить остаток отдельным запросом, потом вставить заказ), между двумя запросами другой пользователь мог бы купить тот же последний товар - возникла бы гонка (race condition). Внутри одной функции PostgreSQL это невозможно: проверка и списание происходят в рамках одного вызова.
- **Триггер аудита цены** и **триггер рейтинга** - поддержание целостности денормализованных и журнальных данных. Если бы пересчёт рейтинга делало приложение, его нужно было бы продублировать в каждом месте кода, которое добавляет отзыв (веб, мобильное приложение, админка, импорт данных) - и любое забытое место привело бы к устаревшему рейтингу. Триггер гарантирует согласованность независимо от того, кто и как вставил строку в `reviews`.

Логику, которая **не связана напрямую с целостностью**, в БД размещать не стоит:

- Расчёт скидок, промокодов, форматирование уведомлений, интеграции с внешними платёжными системами - это бизнес-правила, которые часто меняются, нуждаются в версионировании, и обычно легче читаются и тестируются в коде приложения, чем в PL/pgSQL.
- **seller_revenue** в этом смысле - промежуточный случай: это аналитика, не связанная с целостностью данных напрямую, и её можно было бы вынести в приложение. Я оставила её как функцию БД, потому что она короткая, не содержит бизнес-правил, которые часто меняются.

Итоговый критерий: если логика гарантирует согласованность данных независимо от того, кто и как к ним обращается - её место в БД (функции, триггеры, ограничения). Если логика - это часто меняющееся бизнес-правило или требует сложной отладки и тестирования - её место в приложении.
